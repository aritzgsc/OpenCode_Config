# Entorno opencode 2.x (Windows) + Tor

## Problema
Trabajar con opencode en Windows con un único punto de verdad es frágil por defecto: si se mezclan el background service (`serve --service`) y un servidor explícito (`serve --port`), los plugins se instancian dos veces y las respuestas remotas (por ejemplo, desde el móvil) pueden llegar al servidor equivocado y perderse. Además, exponer el servidor y las notificaciones a internet exige túneles, credenciales y servicios del sistema que no deben filtrarse nunca a un repositorio público. A eso se suma el rate limit del proveedor: sin una IP de salida controlable, un `429` deja la sesión bloqueada contra la misma salida de red. Sin una configuración compartida y sanitizada, cada máquina se configura a mano y publicar esa configuración en GitHub es un riesgo de fuga de secretos.

## Usuarios y casos de uso
- **Desarrollador/a en Windows (usuario principal):** arranca todo el entorno con un solo comando (`opencode-wrapper.ps1`), que levanta Tor, Privoxy, los túneles, un único servidor explícito y la TUI conectada con `--server`. Todo el tráfico externo de OpenCode sale por `Privoxy :8118 → Tor SOCKS :9050 → Internet`; el tráfico local (`localhost`, `127.0.0.1`, `::1`) no pasa por Tor. Trabaja en cualquier proyecto con el pipeline de agentes (`/init`, `/ideas`, `/status`, `/review`, `/documentate`).
- **Desarrollador/a ante rate limit:** el plugin `rate-limit-guard.js` detecta el `429` y pide un circuito Tor nuevo (`SIGNAL NEWNYM`); o pulsa `Ctrl+R` (AutoHotkey) para rotar manualmente. `NEWNYM` solicita circuitos nuevos pero no garantiza una IP de salida distinta en cada rotación.
- **Desarrollador/a en movilidad:** recibe una notificación ntfy en el móvil cuando opencode le hace una pregunta, y responde desde el móvil; el relay del plugin `ntfy.js` la entrega al servidor explícito de su máquina.
- **Persona que clona el repo (configuración inicial):** copia `.env.example` a `.env`, crea su `torrc` local desde `torrc.example` (ver Restricciones), instala el servicio Privoxy (`privoxy.exe --install`), copia los ejemplos de `examples/` (rama `services`) a `C:/ProgramData/opencode` con sus valores reales locales, da de alta los otros 4 servicios con `nssm-register.ps1` y arranca con `opencode-wrapper.ps1`. No necesita adivinar puertos, rutas ni orden de servicios: el README y los ejemplos le dicen qué sustituir en cada fichero.

## Alcance de esta iteración
### Entra
- Servidor único explícito: `opencode-wrapper.ps1` levanta `serve --port ...` y la TUI con `--server ...`; detiene el background service previo para evitar duplicados. Al salir, detiene servidor, túneles, AutoHotkey y Tor (bloque `finally`).
- Salida de red por Tor: `tor.exe` standalone gestionado por el wrapper (SOCKS5 `127.0.0.1:9050`, ControlPort `127.0.0.1:9051`), más Privoxy local (`127.0.0.1:8118`, `forward-socks5t / 127.0.0.1:9050 .`) como puente HTTP→SOCKS. OpenCode usa `HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:8118` y `NO_PROXY=localhost,127.0.0.1,::1`. Tor NO es un servicio Windows: lo inicia y lo detiene el wrapper.
- Rotación de circuitos: `plugins/rate-limit-guard.js` (activo) detecta `429`/cuota en eventos V2 y ejecuta `hooks/rate_limit/rate_limit_handler.bat → rotate_tor.ps1 → SIGNAL NEWNYM`, con cooldown, reintentos y timeout; solo rota si el wrapper fijó `OPENCODE_TOR_RATE_LIMIT_ROTATION_ENABLED=true` (fuera del wrapper, modo observación). Rotación manual con `Ctrl+R` (`hooks/rate_limit/rotar_ip.ahk`, AutoHotkey v2, solo mientras `opencode.exe` está activo).
- Configuración compartida vía `.env` local (servidor, ntfy, relay, rate-limit, Tor, proxy) con plantilla pública `.env.example` (30 claves) con placeholders.
- Relay ntfy (`plugins/ntfy.js`): notifica preguntas al móvil y expone un endpoint local (`OPENCODE_NTFY_RELAY_PORT`) con páginas de respuesta de un solo uso (`/question/:id`, `/form/:id`, TTL `OPENCODE_NTFY_QUESTION_TTL_MS`, olvido tras responder). Persistencia de pendientes en `logs/ntfy_pending.json`, log en `logs/opencode_ntfy.log`.
- Guardia rate-limit (`plugins/rate-limit-guard.js` + `hooks/rate_limit/`): detecta 429/cuota y pide `SIGNAL NEWNYM`; la ruta antigua ADB/modo avión queda eliminada (no queda ni en `deactivated/`).
- Servicios Windows (5 servicios): `privoxy` (instalado con `privoxy.exe --install`, no vía nssm) + `ServidorNtfy` (binario `ntfy.exe` self-host con `server.yml`) + 3 túneles ngrok independientes (`TunnelNgrokOpencode`, `TunnelNgrokNtfy`, `TunnelNgrokCuestionario`), uno por dominio reservado. Arranque con `hooks/tunnel/tunnel-start.ps1` (orden: `privoxy` → `ServidorNtfy` → `TunnelNgrokNtfy` → `TunnelNgrokOpencode` → `TunnelNgrokCuestionario`), parada inversa con `tunnel-stop.ps1`.
- Qué expone cada túnel (a nivel producto): `ngrok-opencode.yml` publica el servidor explícito (auth OAuth Google por email); `ngrok-ntfy.yml` publica el servidor ntfy self-host (mismo puerto que `listen-http` en `server.yml`); `ngrok-cuestionario.yml` publica el relay de preguntas/respuestas (auth en el borde vía `basic_auth` de ngrok, obligatoria al exponer el relay).
- Coherencia de puertos exigida y documentada: `addr` del túnel opencode = `OPENCODE_SERVER_PORT`; `addr` del túnel cuestionario = `OPENCODE_NTFY_RELAY_PORT`; `addr` del túnel ntfy = puerto de `listen-http` en `server.yml`.
- Configuración base versionada y sanitizada: `opencode.jsonc` (modelo por defecto, `experimental.subagent_depth: 2`, MCP Playwright), `cli.json` (keybinds, tema, sesión), `AGENTS.md` (pipeline de agentes + guardia rate-limit), `agents/` (9 ficheros), `commands/` (10), `skills/` (8), `hooks/rate_limit/` (`rate_limit_handler.bat`, `rotate_tor.ps1`, `rotar_ip.ahk`), `plugins/rate-limit-guard.js`.
- Servicios del sistema documentados con ejemplos sanitizados: lo que vive en `C:/ProgramData/opencode` (`server.yml`, `ngrok-*.yml`, binarios `ngrok.exe`/`ntfy.exe`, `cache.db`/`user.db`) se publica solo como ejemplo con placeholders, nunca con valores reales. La config de Privoxy vive fuera del repo (servicio `privoxy`); el `torrc` y `tor-data/` son locales y jamás se versionan.
- Estrategia de ramas: `config` para la configuración sanitizada de `~/.config/opencode` (+ `.env.example`), `services` para los ejemplos de `C:/ProgramData/opencode` (`examples/server.yml`, `examples/ngrok-*.yml`) + instalación nssm (`examples/nssm-register.ps1`, ejecutar elevado una sola vez) + `README-services.md` (tabla qué copiar a dónde y qué sustituir).

### No entra (explícito)
- Valores reales de `.env` (passwords, topics ntfy, tokens, URLs ngrok reales, emails personales, contraseña del ControlPort de Tor) ni de `service.json`: nunca se versionan ni se pegan en el README. Tampoco el `torrc` real (contiene `HashedControlPassword` y rutas locales), ni `tor-data/`, ni dominios `*.ngrok-free.dev` reales ni `basic_auth` real en los ejemplos: solo `tu-dominio*.ngrok-free.dev`, `tu@email.com`, `***`, `C:\Users\TU_USUARIO\...`.
- Ficheros reales de `C:/ProgramData/opencode` (`server.yml`, `ngrok-*.yml` con valores), binarios ni bases de datos reales (`ngrok.exe`, `ntfy.exe`, `cache.db`, `user.db`).
- La arquitectura anterior Cloudflare Workers + Flaregun y la rotación ADB/modo avión: eliminadas, no se documentan como opción.
- Garantía de IP distinta por rotación: `NEWNYM` no la da; queda como limitación conocida pendiente de verificación (ver Supuestos).
- Soporte para macOS/Linux (rutas, wrapper y servicios descritos aquí son Windows).
- Cambios de producto sobre los agentes o comandos: solo se documenta lo que ya existe.

## Criterios de éxito
- Una persona que clona el repo entiende en menos de 5 minutos qué instala, qué copia como `.env`, cómo crea su `torrc` local y qué comando arranca el entorno, sin encontrar ningún secreto real en el repo.
- Esa misma persona sabe configurar los servicios: qué ejemplo copiar a `C:/ProgramData/opencode`, qué placeholder sustituir en cada uno (tabla en `README-services.md`) y que debe ejecutar `nssm-register.ps1` elevado una sola vez.
- `git log --all --full-history -- .env service.json torrc` no devuelve ningún fichero de secretos, y un escaneo de secretos, dominios `*.ngrok-free.dev` reales, emails reales, rutas `C:\Users\<nombre real>` y URLs `*.workers.dev` reales da cero resultados.
- Arrancar `opencode-wrapper.ps1` en una máquina configurada levanta Tor (`9050`/`9051`), Privoxy (`8118`), un solo servidor en el puerto de `.env` y la TUI se conecta sin error; al salir, Tor, puerto y túneles quedan detenidos.
- `Ctrl+R` con OpenCode activo registra `SIGNAL NEWNYM aceptado` en `hooks/rate_limit/rate_limit_handler.log`.
- Recibir y responder una pregunta de opencode desde el móvil funciona cuando los servicios ntfy/ngrok están en marcha.

## Restricciones conocidas
- Solo Windows: wrapper en PowerShell, servicios Windows con nssm, rutas `~/.config/opencode` y `C:/ProgramData/opencode`.
- Requisitos: Windows con PowerShell; Node o Bun para plugins; opencode `2.0.8` (`@opencode/plugin 2.0.8`); nssm para 4 servicios (`ServidorNtfy` + 3 ngrok); Tor Expert Bundle (`tor.exe` standalone, ruta en `OPENCODE_TOR_EXE`); Privoxy descargado de la página oficial e instalado como servicio con `.\privoxy.exe --install` (PowerShell elevado desde su carpeta), con `forward-socks5t / 127.0.0.1:9050 .` en su `config.txt` (`listen-address 127.0.0.1:8118` viene por defecto); AutoHotkey v2 para `Ctrl+R`; **3 cuentas ngrok separadas** (una por túnel: opencode, ntfy y cuestionario, cada una con su dominio reservado `tu-dominio*.ngrok-free.dev`); servidor ntfy self-host (`ntfy.exe` + `server.yml`); Playwright MCP (`npx -y @playwright/mcp@latest`); cuenta Google para el OAuth del túnel opencode (`allow_emails`). Opcional para diagnóstico: Npcap + Wireshark sobre el adaptador loopback (ver Supuestos).
- Puertos fijos locales: Tor SOCKS `127.0.0.1:9050`, Tor ControlPort `127.0.0.1:9051`, Privoxy `127.0.0.1:8118`. Si otro Tor ocupa `9050`/`9051`, el wrapper aborta en vez de interferir.
- El `torrc` es local y nunca se versiona (ignorado en `.gitignore`, igual que `tor-data/`). Plantilla mínima: `SocksPort 127.0.0.1:9050`, `ControlPort 127.0.0.1:9051`, `CookieAuthentication 0`, `HashedControlPassword` generado con `tor.exe --hash-password "<tu-secreto>"` (ese secreto va a `OPENCODE_TOR_CONTROL_PASSWORD` en `.env`), `DataDirectory` y `Log notice file` con rutas de la máquina (`%USERPROFILE%\.config\opencode\...`, nunca otra cuenta).
- El arranque/parada de túneles requiere elevación de administrador (UAC): el wrapper invoca `tunnel-start.ps1`/`tunnel-stop.ps1` con `-Verb RunAs`; sin admin aborta. El alta inicial con `nssm-register.ps1` también exige PowerShell elevado.
- Lo público debe usar placeholders: `***` para secretos, `tu-dominio*.ngrok-free.dev` para dominios, `tu@email.com` para emails, `C:\Users\TU_USUARIO\...` para rutas de usuario. Nunca `.env` real, solo `.env.example`; nunca `torrc` real ni `*.yml` reales de `C:/ProgramData/opencode`, solo `examples/`.
- `.env`, `service.json`, `torrc`, `tor-data/`, `logs/`, binarios (`*.exe`) y bases de datos (`*.db`) están ignorados y nunca se versionan.

## Supuestos
- El lector parte de una instalación funcional (Node/Bun, opencode 2.0.8, nssm, ngrok, ntfy, Tor Expert Bundle, Privoxy, AutoHotkey v2) o la instala siguiendo la guía de la rama correspondiente; este README no es un instalador paso a paso.
- `.env.example` existe en la rama `config` con todas las claves necesarias (servidor, ntfy, relay, rate-limit, Tor, proxy — 30 claves) y cada valor es un placeholder. `OPENCODE_TOR_RATE_LIMIT_ROTATION_ENABLED` NO va en `.env`: la fija el wrapper a `true` solo durante su ejecución.
- La rama `services` contiene ejemplos de `server.yml` y `ngrok-*.yml` con placeholders, `nssm-register.ps1` y `README-services.md` con la tabla de correspondencia ejemplo → destino real; los comandos nssm no contienen credenciales reales.
- La guardia rate-limit está activa (plugin + `hooks/rate_limit/`), pero con una limitación conocida: `SIGNAL NEWNYM` solo pide circuitos nuevos para conexiones nuevas; no garantiza IP distinta (mismo relay de salida posible) ni se ha verificado aún que el retry de OpenCode tras un `429` abra siempre una conexión TCP/TLS nueva en vez de reutilizar una del pool de `fetch`/Bun. Verificación propuesta: Wireshark sobre el adaptador loopback (Npcap) observando OpenCode→Privoxy→Tor antes y después de rotar. Hasta entonces, no afirmar que `429 → NEWNYM → retry` implique IP nueva.
